# v6 — 装饰器增强与流式输出（收官）

> `v6_boost_stream.py`，1256 行。评测：**8/9，与 v5 逐题相同**——v6 是
> 架构收官，不动检索质量；它兑现的是 v1 埋下的两个伏笔。

## 核心洞察

**`next()` 先行的装饰器模式不是教学玩具，WikiBoost 是它在生产代码里的真实
用法；流式输出证明「插件链」和「流式生成」这两个正交机制可以共存、互不阻塞。**

v1 的 LoggingBoost 只往 debug 里塞了一条痕迹；v6 把它换成三件真家伙：

```
CHUNK_RERANK:  PluginRerank ──next()──> PluginTypeBoost（×1.3 + 稳定重排）
INTO_CHAT_MESSAGE:  合并结果 → <context id="N">…</context> → 模板渲染
CHAT_COMPLETION_STREAM:  起后台线程消费流 → 发事件 → 立刻 return next()
```

## 运行方式

```bash
python v6_boost_stream.py --query "如何重置青鸟的 API 密钥？" --mock  # 观察逐块输出
python v6_boost_stream.py --eval --mock                              # 8/9，与 v5 持平
python -m pytest tests/test_v6_boost_stream.py
```

## 代码走读

### 1. PluginTypeBoost：装饰器毕业礼（↔ `wiki_boost.go:37-97`）

```python
def on_event(self, event_type, state, next):
    err = next()                    # :49-51 先让精排跑完，错误原样上抛
    if err is not None:
        return err
    if not any(r["chunk_type"] == self.chunk_type for r in state.rerank_result):
        return None                 # :53-64 快速路径：连重排都不做
    ...  # ×1.3（:15,:80-86）→ 稳定重排（:90-93）
```

生产实例 boost 的是 `wiki_page`（LLM 预综合的知识优于原始文档块）；课程语料
没有 wiki，用 `faq` 演示同一机制。三个值得较真的细节：

- **它的「后置」地位来自注册顺序**：`build_manager` 里 TypeBoost 注册在
  PluginRerank 之后（内层），对照 container.go:323 vs :336 的同款关系——
  v1 文档辨析过的「next() 打到终止 no-op」在这里真实上演；
- **快速路径保护 MMR**：没有目标类型时什么都不做——一旦做了重排，MMR 的
  多样性次序就没了；
- **boost 生效时的重排是全列表按分数稳定排序**（:90-93）：MMR 次序会被覆盖，
  生产代码接受了这个副作用。课程用模拟实验证实了它（q2 的 rel-v2-01/bp-02
  在 boost 触发后按分数归位），并有单测钉住两种路径。

评测影响：boost 在 q1/q2/q8/q9 上生效（池里有 faq），PASS 集合零变化——
faq-02 的分数从 0.504 抬到 0.655，名次本来就是第一。**增强插件的理想状态
恰恰是这样：改变分数结构、不破坏正确性**，它的价值要在 wiki/FAQ 混合库里
才充分显现。

### 2. PluginIntoChatMessage：模板渲染取代裸拼接（↔ `into_chat_message.go:31-199`）

v0-v5 的 `build_prompt` 是字符串拼接；v6 按真实实现改成两段式：

```python
contexts = "\n".join(f'<context id="{i+1}">{r["content"]}</context>' ...)  # :155-161
state.user_content = render_placeholders(CONTEXT_TEMPLATE,
    {"contexts": contexts, "query": state.query, "language": "中文"})       # :167-171
```

`<context id="N">` 标签让下游模型可以按编号引用资料（真实系统的引用溯源
就建在这上面）；模板本体压缩自 `context_template.yaml:38-57` 的
detailed_context（任务描述 + 参考资料 + 问题 + 回答要求 + 语言规则）。
两个容易忽略的行为：**非检索意图也走模板**（contexts 为空，:80-110），
且此时 query 用的是**改写后**的版本——直接对话时改写质量往往更好；
检索路径的 query 则用**原话**（改写只喂检索，v2 的老规矩）。

未实现（租户配置门控）：FAQ 优先级分节渲染（`<source type="faq"
priority="high">`，:134-153）、文档元数据头（:122-131）、图片描述/附件
注入（:173-184）。

### 3. PluginChatCompletionStream：fire-and-forget（↔ `chat_completion_stream.go:41-238`）

洋葱链是同步的：`trigger` 要等每个插件的 `on_event` 返回。流式生成动辄
几十秒——如果生成插件等流跑完，整条链就挂在那里。真实实现的解法只有三行
结构：

```python
stream = stream_fn(messages)      # :87 建流（失败是同步可见的错误 :88-94）
threading.Thread(target=consume).start()   # :112-235 后台消费，往 EventBus 发事件
return next()                     # :237 立刻交棒——不等流跑完
```

Python 的 `threading.Thread + queue.Queue` ↔ Go 的 `goroutine + channel`；
`EventBus` ↔ `chatManage.EventBus`（另一端是 SSE handler）。纪律照抄：
EventBus 缺失是硬错误（:71-76，流式没有出口就没有意义）；流中途出错发
error 事件而不是让线程悄悄死掉（:182-198）；channel 自然关闭要补 done
（:172-179）。

**fire-and-forget 的直接证明**（单测 `test_stream_plugin_returns_before_
stream_finishes`）：把流卡在一道 `threading.Event` 闸门后面——`trigger`
照样返回、`state.answer` 还是空串；放行闸门后事件逐块到达、答案完整拼装。
如果插件在等流，`trigger` 会卡死在闸门上。

课程简化：不做 thinking/答案双通道分流（:200-232）、引用展开与资源解码器
（:113-160 的 StreamDecoder/StreamExpander）、ctx 取消监听（:164-170）。

## 这个版本证明了什么 / 牺牲了什么

**证明了**：
- v1 的洋葱骨架撑到了最后一版：v6 的三个新能力全部是「挂插件」，
  EventManager 六个版本零改动；
- 装饰器模式在生产语境下的完整形态：快速路径、错误上抛、重排副作用；
- 同步插件链与异步流式生成可以干净解耦——代价只是一个事件总线。

**牺牲了（这是课程的边界，不是下一版的预告）**：
- 多模态（图片子块、VLM 描述）、Web 检索、实体图检索、数据分析——SPEC
  明确排除的旁支；
- 多租户/权限/审计/并发治理——工程基础设施；
- q3 的最后半步——需要真实 cross-encoder，机制本身已有单测证明。
