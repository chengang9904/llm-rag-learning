# v0 — 朴素检索问答（Naive RAG）

> `v0_naive_rag.py`，131 行（核心链路约 70 行，其余是 --mock / --eval 辅助）。
> 无框架、无插件链、无任何检索后处理。

## 核心洞察

**检索 + 拼接就是 RAG 的最小骨架，后续所有版本都是在这个骨架上做手术。**

整条链路只有五步：

```
用户问题 ──> embedding 查询 ──> 余弦 top-k ──> 原样拼进 prompt ──> 调 LLM
              【模型调用】      【代码算法】     【代码算法】       【模型调用】
```

WeKnora 生产链路里的十几个插件（查询理解、混合检索、RRF 融合、精排、MMR、
合并四术、装饰器、流式输出），本质上都是往这五步之间插入的「手术」。v0 的价值
在于：先看清没有这些手术时，同一组问题会坏在哪里——本文最后一节逐题记录。

## 运行方式

```bash
python v0_naive_rag.py --query "如何重置青鸟的 API 密钥？" --mock   # 单条提问
python v0_naive_rag.py --eval --mock                                # 跑完整评测集
python -m pytest tests/test_v0_naive_rag.py                         # 单元测试（无需网络）
```

去掉 `--mock` 走真实 OpenAI 兼容 API（需 `.env`，见 `.env.example`）。

## 代码走读

### 1. 只索引叶子块（`load_chunks`）

```python
return [c for c in json.load(f) if c["chunk_type"] != "parent_text"]
```

`corpus/chunks.json` 里有一个 822 字的父块 `arch-parent`，被刻意排除在索引外。
这不是偷懒：真实系统同样只对子块建索引（子块小、语义集中、召回准），父块要等
v5 的合并阶段按 `parent_chunk_id` 「还原」出来。v0 把这条线索埋在第一行。

### 2. Mock embedding 是词面匹配的向量化伪装（`mock_embed`）

```python
grams = [text[j:j + n] for n in (2, 3) for j in range(len(text) - n + 1)]
for g in grams:
    h = int(hashlib.md5(g.encode("utf-8")).hexdigest(), 16)
    mat[i, h % MOCK_DIM] += 1.0 if (h >> 16) % 2 else -1.0
```

把字符 2/3-gram 经 MD5 哈希投进 256 维（带 ± 符号的特征哈希），行向量归一化后，
余弦相似度 ≈ 字符 n-gram 重合度。它完全确定（同一文本永远得到同一向量，不依赖
`PYTHONHASHSEED`），所以能做精确断言的单元测试；同时它是个**词面**匹配器——
这个性质在评测记录一节会变成有趣的教学素材。

### 3. 余弦 top-k（`cosine_top_k`）

```python
scores = chunk_mat @ query_vec
order = np.argsort(-scores, kind="stable")[:k]
```

所有向量已归一化为单位长度，点积即余弦。`kind="stable"` 保证同分时按语料顺序取，
检索结果完全可复现——`tests/test_v0_naive_rag.py` 对排序、平分、截断各有断言。

### 4. 原样拼接（`build_prompt`）

检索命中的块带着 `[chunk_id]` 直接串起来塞进 prompt。没有去重、没有重叠消除、
没有 FAQ 格式化、没有父块还原——q3 的评测结果会展示这有多粗糙。

### 5. 生成（`generate`）

一次非流式 `chat.completions` 调用。`--mock` 时返回占位文本，让无 Key 环境也能
验证整条链路的结构。

### mock 与真实 embedding 的镜像关系

这是 v0 最值得咀嚼的现象：`--mock`（词面 n-gram）与真实语义向量**在 q6/q7 上
互为镜像**——

- mock 模式：q6/q9（错误码、配置项）稳定 PASS，q7（口语化问法）必然 MISS；
- 真实 embedding：q7 预期命中，而 q6/q9 这类「精确 token」题反而不稳定。

也就是说，**无论选哪一种单路检索，总有一半盲区**。这不是 v0 实现得不好，
而是单路检索的结构性缺陷——v3 之所以要向量、关键词两路并行再做 RRF 融合，
理由已经完整地躺在这张评测表里了。

## 这个版本证明了什么 / 牺牲了什么

**证明了**：~70 行核心代码就能跑通「检索增强生成」的完整闭环，且纯代码路径
（余弦 top-k）可以离线精确测试。

**牺牲了**（各自的救兵）：

- 一切都硬编码在 `main` 的顺序调用里，加任何一步都要改主流程 → v1 插件链
- 用户原话直接当检索 query，改写、意图、历史一概不管 → v2 / v5
- 单路向量检索，词面与语义各有一半盲区，召回不足没有补救 → v3
- 检索分数即最终排序，近重复内容无人去重 → v4
- 命中什么拼什么：碎片、重叠、FAQ 原文直接进 prompt → v5
- 一次性返回，无装饰器扩展点，无流式 → v6

## 对照 WeKnora 真实实现

**v0 刻意不对应任何单一文件**——它是把 WeKnora 整条 chat pipeline 的工程化
全部剥掉之后剩下的裸骨架。对照关系是「v0 的每一步 ↔ WeKnora 的哪一段被省略了」：

| v0 的做法 | WeKnora 的真实做法 |
|-----------|-------------------|
| `main` 里顺序调用五个函数 | `chat_pipeline.go:53-68` 把插件右折叠成洋葱链，`session_knowledge_qa.go:658-795` 按事件驱动 |
| 用户原话直接检索 | `QUERY_UNDERSTAND` 事件先做 LLM 改写+意图分类（`query_understand.go:58-161`） |
| 单路余弦 top-k | `CHUNK_SEARCH_PARALLEL`：向量+关键词并行（`search.go:99-118`），RRF 融合（`knowledgebase_search_fusion.go:80-142`），低召回时启发式查询扩展（`query_expansion.go:136-160`） |
| 检索分即排序 | `CHUNK_RERANK`：cross-encoder + 复合分数 + MMR（`rerank.go`），WikiBoost 装饰（`wiki_boost.go:42-97`） |
| 原样拼接 | `CHUNK_MERGE`：父块还原/重叠拼接/FAQ/短块扩展/历史片段（`merge*.go`），再 `FILTER_TOP_K` |
| 一次性生成 | `INTO_CHAT_MESSAGE` 模板渲染 + `CHAT_COMPLETION_STREAM` 流式（`chat_completion_stream.go`） |

顺着这张表往下走，就是 v1–v6 的目录。
