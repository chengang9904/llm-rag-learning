# v5 — 上下文合并四术

> `v5_merge.py`，1183 行（检索/理解/精排沿用 v1-v4）。
> 评测：**8/9**（判定升级为「覆盖命中」）——v4 的 q4 回归被治愈，
> q3 剩下最后半步，成为 mock 模式的诚实边界。

## 核心洞察

**检索选完的是碎片，合并阶段才是把碎片重新变回「人能读的上下文」的地方——
这一步的工程量不比检索算法本身小。**

精排给了我们 5 条「最相关的碎片」，但直接拼进 prompt 会是什么样？父块的
一小段（掐头去尾）、两段有 98 字重复的部署步骤、一条裸的 Q/A 原文、一个
174 字的孤零零函数签名。合并阶段做四种「手术」把它们变回完整语境：

| 手术 | 症状 | 疗法 | 对照 |
|------|------|------|------|
| 父块还原 | 命中的子块只是完整章节的切片 | 子块 → 完整 parent_text（子块只是命中的证据，语境在父块里） | `merge.go:215-341` |
| 重叠拼接 | 相邻块带重复段落，各自不完整 | 同源同类型按 StartAt 排序，文本匹配去重后缝合 | `merge_overlap.go:15-78` |
| FAQ 格式化 | Q/A 原文混在普通资料里 | 渲染成 `Q: …\nAnswer:\n- …` 结构 | `merge_faq.go:11-97` |
| 短块扩展 | <350 字的块缺上下文 | 沿 pre/next 链拉邻居，拼到 350~850 字 | `merge_expand.go:10-252` |

外加**历史相关片段注入**（上一轮检索过的块，Jaccard≥0.15 才要、分数打 6 折、
最多 3 条，`merge_history.go:17-85`），最后 `FILTER_TOP_K` 确定性排序后截断
（`filter_top_k.go`——整条链最朴素的一步，不配单开一个版本）。

## 代码走读

### 0. 八步流水与两次拼接（↔ `merge.go:44-96`）

```
选输入(rerank优先) → 去重(id+签名) → 注入历史 → 父块还原
  → 分组重叠拼接 → FAQ 格式化 → 短块扩展 → 再拼接一轮 → 终去重+部分重叠剔除
```

顺序本身就是教案：**先还原父块再拼接**（还原后同父的子块变成重复区间，正好
被拼接吸收）；**扩展之后要再拼一轮**（扩展会造出新的重叠区间，`merge.go:89`
的注释写得明明白白）；**去重做三次**（进门一次、终点两种——id/签名去重 +
「内容被大体包含」的部分重叠剔除，`search.go:199-260`，阈值 0.85）。

### 1. sub_chunk_ids：合并的账本（↔ `SubChunkID`）

三种手术都在维护同一个字段：父块还原记下命中的子块（`merge.go:339-341`）、
重叠拼接记下被缝合的块（`merge_overlap.go:45,56`）、短块扩展记下拉进来的
邻居（`merge_expand.go:218-227`）。**从本版起评测判定升级**：期望块 id 出现
在结果的 `{自身 id} ∪ sub_chunk_ids` 里即算命中——内容进了 prompt 才算数，
按检索 id 判会漏记合并阶段的功劳。这不是课程发明：WeKnora 用同一字段驱动
前端的引用溯源。

### 2. 重叠拼接靠文本匹配，不靠位置裁剪（↔ `chunkmerge.go:38-68`）

```python
for k in range(max_k, MIN_OVERLAP_RUNES - 1, -1):   # 从最长后缀往短找
    needle = acc[-k:]
    pos = nxt.find(needle)
    if 0 <= pos <= head_slack:
        return acc + nxt[pos + k:]
```

源码注释交代了原因：分块器补写的表头、HTML 实体，都会让 content 长度与
`EndAt-StartAt` 不一致——按位置裁剪会丢字或重复。`StartAt/EndAt` 只用来
估算搜索窗口；真正的重叠由文本匹配确认。两个常量都有讲究：后缀短于
**12 字符**不参与匹配（`|---|` 这类表格分隔行会误配，`:27`）；搜索窗口下限
**400**（位置信息缺失时兜底，`:30`）。课程语料 offset 逐字符真实，单测里
deploy 三连块拼回后**恰好等于原文切片**——这是 v0 设计语料时埋的种子。

### 3. 短块扩展的细节（↔ `merge_expand.go`）

- 长度单位是 **rune 数**（`runeLen`，`:255-257`）——与 v3 查询扩展的字节数
  不同，同一个代码库里两种长度语义并存，读源码时极易踩坑；
- 只扩 `text` 类型：FAQ 是自包含的 Q/A，扩它只会引来隔壁问题的答案（`:46-48`）；
- 基底用**原始块内容**（回表取，`:126-127`），不是流水线上可能已被改写的
  content；
- 先各取一个前后邻居，不够再交替伸展（先前后再，`:141-209`），`concatNoOverlap`
  消除邻居间的重复前后缀，最终截断在 850；
- 停止条件是 `≥350` 而不是「越多越好」——上下文不是免费的，这个区间是
  生产调参的产物。

### 4. 历史注入的三道闸（↔ `merge_history.go:17-85`）

上一轮检索过的块不是白捡的上下文：① 与**本轮**问题 Jaccard≥0.15 才要
（旧引用可能已经跑题）；② 分数 ×0.6（旧货打折，别压过新检索的同分结果）；
③ 最多 3 条（别让陈年引用淹没本轮上下文）。本轮已检回的块跳过——q8 的
faq-03 就属于这种情况（改写已把它救回来了，历史注入按 `existingIDs` 去重
静默让路，机制间互不打架）。

### 5. FILTER_TOP_K：最朴素的一步为什么还要排序（↔ `filter_top_k.go:76-99`）

合并阶段经过了 map 分组，同分结果的顺序会漂移。截断前先做**多级 tiebreaker
的确定性排序**（分数 → knowledge_id → chunk_type → start → end → id），
保证同一请求永远得到同一批 top-k——可复现性是工程要求，不是算法要求。

`python v5_merge.py --eval --mock`：**8/9**（v4 为 7/9，判定升级为覆盖命中）。

| 质变 | q6/q7/q9 | 全部带上邻居：`err-02(+err-01,err-03)`、`bp-01(+bp-02)`、`err-03(+err-02)`——短块语料在扩展后个个变成完整语境 |
| 仍 MISS | q3 | `deploy-01(+deploy-02)`——扩展从 337 字拉到 462 字就到了 350 的停止线，deploy-03 没进来。根因在 v4：mock cross-encoder（词面召回）认不出「第三步/第四步」与「完整步骤」的语义关联，deploy-02/03 在精排就被滤掉了。**重叠拼接机制本身是好的**——单测里把三块直接喂给 `merge_overlapping_chunks`，拼回结果与原文切片逐字符相等。真实 cross-encoder 下这三块会活着走到合并阶段 |

**q3 是词面 mock 的诚实边界**：v0 讲过「mock 与真实 embedding 互为镜像」，
到 v5 这个镜像的最后一块碎片仍然立着——它标记的是伪模型的能力上限，
不是管线的缺陷。

## 这个版本证明了什么 / 牺牲了什么

**证明了**：
- 合并四术各自独立可测（26 项单测），并且**顺序即语义**：还原→拼接→格式化→
  扩展→再拼接，换序就出错；
- `sub_chunk_ids` 账本让「上下文里到底有什么」变得可追溯——评测判定升级
  依据的是真实系统同款字段；
- q4 的修复路径证明了合并与检索是互补的两条腿：检索没找到的内容，链接
  结构可以补回来。

**牺牲了（谁来补）**：
- LoggingBoost 还是教学玩具，真正的装饰器（先 `next()` 后 ×1.3 重排）
  该挂在精排事件上 → v6 WikiBoost 模式
- 生成仍是一次性返回、上下文模板是裸拼接 → v6 流式输出 + 模板渲染
- 未实现（多模态/多租户基础设施）：图片子块的祖父链还原（`merge.go:343-385`）、
  ImageInfo 合并（`merge_overlap.go:80-134`）、FAQ 结构化元数据回表
  （课程语料 FAQ 内容本身就是 Q/A 文本，直接解析渲染）
