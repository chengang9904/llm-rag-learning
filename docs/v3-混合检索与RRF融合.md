# v3 — 混合检索、RRF 融合与低召回查询扩展

> `v3_hybrid_fusion.py`，685 行（洋葱引擎与查询理解沿用 v1/v2）。
> 评测：**7/9**，语义题 q7 被两路融合救回；近重复对首次同时进入候选池
> （v4 的问题由此真实产生）。

## 核心洞察

**RRF 不比较分数量纲，只比较排名——这是它能跨异构检索引擎融合的原因。**

向量分是余弦（各引擎量纲还不一样），BM25 分无上界（本语料实测 2~19），
两者做加权平均毫无意义。RRF 把两路各自的**排名**换算成分数再加权：

```
score(chunk) = 0.7/(60 + 向量路名次) + 0.3/(60 + 关键词路名次)
```

k=60 是平滑常数：名次 1 与名次 2 的分差被压平（1/61 vs 1/62），单路内的
微小排序差异不会主导融合结果；两路**都**命中的 chunk 拿两份贡献，自然浮到
顶部。配套的第二个洞察：**查询扩展是「零成本换召回率」**——不调 LLM，用
纯字符串规则生成变体重新检索，与 v2 查询理解「一次 LLM 调用换准确率」形成
对照。

```
              ┌─ 向量路：余弦 → 按引擎归一化到 [0,1] → 阈值 → top-10 ─┐
query ──并行──┤                                                        ├─ 融合/退化 ─→ 候选池
              └─ 关键词路：BM25 原始分（不归一化）→ 阈值 → top-10 ────┘      │
                                                            候选数 < 10 ─────┘
                                                            → 启发式变体 ×5 并发重检索（尾部追加）
```

## 代码走读

### 1. 为什么向量分归一化、关键词分不归一化（↔ `normalizer.go`）

`normalize_score` 只处理向量分（:117-121 对 BM25 直通）：BM25 的量纲无上界，
硬压到 [0,1] 会压塌长尾；反正下游 RRF 只看排名。向量分则要按**引擎**归一化
（:123-157）：本课程的内存引擎暴露原始余弦 ∈ [-1,1]，与 Milvus 同组走
`(s+1)/2`（:124-130）；pgvector/ES/Qdrant 等到手已是 [0,1]，只做 `clamp01`
（:131-153）。`clamp01` 连 NaN/Inf 都要接住（:163-174）——NaN 会破坏下游
排序的严格弱序，这是生产代码才会想到的细节。

### 2. 融合还是退化（↔ `knowledgebase_search_fusion.go:33-50`）

**只有两路都有结果才 RRF**。任何一路为空就退化为另一路的按分去重
（`deduplicate_by_score`，:65-78：同 id 保留最高分）——对单路做 RRF 不仅
无意义，还会把仅剩一路的原始分数抹掉（注释特意标注「对 FAQ 场景很重要」）。

### 3. RRF 的实现细节（↔ `:84-142`）

三个容易漏掉的点，全部有单测钉住：

- 排名 **1-indexed**，同 id 重复出现取**首次出现**的名次（:89-100）；
- 元数据优先取**向量路**的那份（:103-113）——关键词引擎往往只回 id 和分数；
- 只在一路出现的 chunk 只拿那一路的贡献，不做惩罚。

### 4. 查询扩展：四种零成本变体（↔ `query_expansion.go:110-171`）

触发条件：融合后候选数 `< max(1, EMBEDDING_TOP_K)`（↔ `search.go:127-132`）。
变体生成完全本地、无 LLM：① 去停用词关键词串（:137-140）② 引号短语
（:143-146）③ 分隔符切段（:149-154）④ 去疑问词前缀（:156-160，正则逐字
照抄 :187）。上限 5 个（:163-165），与原查询/改写查询重复的丢弃。

忠实复刻的一个冷门细节：Go 的 `len()` 是**字节**长度——「段长 >5」意味着
两个汉字（6 字节）就能通过、而 5 个 ASCII 字母不行。Python 版用
`len(s.encode("utf-8"))` 复刻，测试
`test_expand_segment_needs_more_than_5_bytes` 钉死。

扩展重检索：每变体并发（上限 16，↔ :36-43），**关键词阈值 ×0.8、向量阈值
不变**（↔ :29,55-58）——扩展本来就是为了补关键词召回，放宽的只有关键词那路。

### 5. 一个诚实的课程简化：扩展命中只追加在尾部

主结果是 RRF 分（~0.01 量级），扩展命中可能是另一次融合、甚至单路退化的
原始分（BM25 4.2！）——**两种量纲不可比**。WeKnora 敢把它们混在一起，是
因为下游 `CHUNK_RERANK` 会对全体候选统一重打分；v3 还没有精排，只能把扩展
命中追加在尾部保住主排序。跑一下扩展演示查询就能亲眼看到量纲混杂：

```
检索命中 rel-v1-01    score=0.011475 (rrf)
检索命中 deploy-03    score=0.004918 (rrf)
检索命中 err-02       score=4.234159 (keyword)   ← 扩展带回的原始 BM25 分
```

这就是 v4 精排「统一重打分」的第一个存在理由。

## 这个版本证明了什么 / 牺牲了什么

**证明了**：
- 混合检索的必要性不是理论——q7 的翻正就是两路互补的实证；q6/q9 从「靠 mock
  巧合」变成「有关键词路背书」；
- RRF 用排名而非分数融合，绕开了「异构量纲不可比」这个死结；
- 召回不足时存在零成本的补救（启发式变体），不是所有增强都要花 LLM 调用。

**牺牲了（谁来补）**：
- 候选池排序仍由检索分决定：q5 的近重复对挤在一起、q8 的 faq-04 仍压着
  faq-03、扩展命中的量纲混杂只能藏在尾部 → **v4 精排统一重打分 + MMR 去冗余**
- q3 的三个重叠块凑不进 top-3，就算凑进也是带重复段落的碎片 → v5 合并
- 真实系统的并行还包括实体/图检索（`CHUNK_SEARCH_PARALLEL` 事件内），
  Neo4j 门控，课程不涉及
