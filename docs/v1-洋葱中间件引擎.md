# v1 — 洋葱式中间件插件引擎

> `v1_pipeline_engine.py`，296 行（其中约 90 行与 v0 逐字相同——直接
> `diff v0_naive_rag.py v1_pipeline_engine.py` 就能看到纯粹的结构增量）。
> 检索能力与 v0 完全相同，评测结果也完全相同（5/9）——这是刻意的。

## 核心洞察

**`next()` 就是整个中间件系统的秘密；注册顺序即链序。**

v0 的五步硬编码在 `main` 里，加任何一步都要改主流程。v1 把它重构成
「事件 + 插件链」：每个事件挂着一串插件，运行时被**右折叠**成嵌套闭包——

```
trigger(CHUNK_SEARCH)
  └─> PluginSearch.on_event            ← 注册在先 = 洋葱外层
        │ 检索、写入 state.search_result   （前置逻辑）
        └─> next() ──> PluginLoggingBoost.on_event   ← 注册在后 = 内层
                         └─> next() ──> 终止 no-op
                         往 state.debug 叠加信息        （后置逻辑）
```

一个插件只需要决定两件事：**在 `next()` 之前做什么、在 `next()` 之后做什么**。
不调用 `next()` 就是短路——下游整条链都不会执行。这与 Express/Koa 的中间件
完全同构，WeKnora 用它组织了整条生产 RAG 链路。

## 代码走读

### 1. 右折叠（`EventManager._build_handler` ↔ `chat_pipeline.go:53-68`）

Go 原版：

```go
next := func(context.Context, types.EventType, *types.ChatManage) *PluginError { return nil }
for i := len(plugins) - 1; i >= 0; i-- {
    current := plugins[i]          // ← 循环变量快照
    prevNext := next
    next = func(ctx ..., chatManage ...) *PluginError {
        return current.OnEvent(ctx, eventType, chatManage, func() *PluginError {
            return prevNext(ctx, eventType, chatManage)
        })
    }
}
return next
```

Python 复刻：

```python
nxt = terminal                        # 链条尽头的 no-op
for plugin in reversed(plugins):
    def wrapped(event_type, state, plugin=plugin, prev_next=nxt):
        return plugin.on_event(event_type, state,
                               lambda: prev_next(event_type, state))
    nxt = wrapped
return nxt
```

从终止 no-op 开始**倒序**包裹，最终 `plugins[0]` 在最外层。两个语言版本
都要处理同一个坑：闭包捕获的是变量而不是值——Go 版用 `current := plugins[i]`
（chat_pipeline.go:59）快照，Python 版用默认参数 `plugin=plugin, prev_next=nxt`
快照。少了这一行，所有层都会引用同一个（最后的）插件。

### 2. 注册即重建（`register` ↔ `chat_pipeline.go:40-51`）

每注册一个插件，它声明的每个事件的调用链都**整条重建**一次。链是注册完成
时就折叠好的静态结构，不是每次 trigger 时动态查找——这也是「注册顺序即
链序」的实现层含义。

### 3. 两种插件写法（对照真实源码里的一对搭档）

WeKnora 的 `CHUNK_RERANK` 事件上挂着两个插件，注册顺序（container.go:322-336）
决定了 Rerank（:323）在外层、WikiBoost（:336）在内层：

- **前置逻辑风格**（`PluginSearch` ↔ `rerank.go:38-266`）：先做自己的事，
  最后 `return next()` 交棒。Rerank 的每条退出路径——包括跳过与降级——
  都以 `return next()` 结尾（rerank.go:42,55,61,143,176,265），保证链条
  永远走得下去。
- **后置逻辑风格**（`PluginLoggingBoost` ↔ `wiki_boost.go:42-97`）：
  先 `err = next()`（错误原样上抛，wiki_boost.go:49-51），再对 state 里
  已就位的结果做后处理。**不改上游一行代码，就能往结果上叠加行为**——
  这就是装饰器。

一个容易读错的细节：WikiBoost 的 `next()` 打到的其实是链条尽头的 no-op
（它是最内层插件），并不是「调用 next() 去执行 Rerank」。它的「后置」地位
来自**注册在后（内层）+ next() 先行**的组合：Rerank 作为外层先做完全部工作
才交棒进来。理解了这一点，才算真正理解「注册顺序即链序」。

### 4. 驱动循环（`run_pipeline` ↔ `session_knowledge_qa.go:658-795`）

`KnowledgeQAByEvent` 拿着一个事件列表逐个 `Trigger`（:717），任一插件返回
错误即中止并走兜底。事件列表本身是按需拼装的（`AddIf(hasHistory,
types.LOAD_HISTORY)`，:181-187）——v1 的 `run_eval` 借这个思路只触发
`CHUNK_SEARCH`：评测不需要生成，就不触发生成事件。

### 5. `PluginError`（↔ `chat_pipeline.go:81-125`）

插件返回 `None` 表示成功、返回 `PluginError` 表示失败。预定义错误
（`ERR_SEARCH_NOTHING` ↔ `ErrSearchNothing`）让驱动层能按错误类型区分
「没检索到内容」（走兜底回答）和「真正的故障」。

## 这个版本证明了什么 / 牺牲了什么

**证明了**：把线性脚本重构成插件链，行为可以一比一保持；而代价换来的是——
从 v2 起，每个新能力都只是「往链上挂一个新插件」，不再碰主流程。
LoggingBoost 已经演示了最小的例子：不改 PluginSearch 一行代码，往检索结果
上叠加了 debug 信息。

**牺牲了（下一版本会补上什么）**：

- 链上仍然只有 v0 的两步逻辑，没有任何新算法——v2 起逐个补：查询理解（v2）、
  混合检索与 RRF（v3）、精排与 MMR（v4）、合并四术（v5）
- LoggingBoost 只是装饰器的教学玩具，真正有意义的 Boost（×1.3 重排）在 v6
- 事件只有两个；真实系统的 `LOAD_HISTORY`/`QUERY_UNDERSTAND`/`CHUNK_RERANK`/
  `CHUNK_MERGE`/`FILTER_TOP_K` 等会随后续版本逐个出现
