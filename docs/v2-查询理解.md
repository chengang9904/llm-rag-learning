# v2 — 查询理解（Query Understanding）

> `v2_query_understanding.py`，470 行（洋葱引擎与基础设施沿用 v0/v1，
> `diff v1_pipeline_engine.py v2_query_understanding.py` 可见增量）。
> 评测：**6/9**，历史依赖题 q8 从 MISS 翻到 PASS。

## 核心洞察

**查询理解是「花一次 LLM 调用换取更准的检索输入」，而且必须发生在检索之前——
它是链条里第一个真正做事的插件。**

用户的原话经常不是好的检索 query：「那超出之后呢？」里没有任何可检索的关键词，
「超出」的主语躺在上一轮对话里。v2 在检索前插一个 `QUERY_UNDERSTAND` 事件，
一次 LLM 调用同时做两件事：

1. **查询改写**：指代消解 + 省略补全，把「那超出之后呢？」变成
   「免费版每月的消息配额是多少，那超出之后呢？」——检索吃改写后的版本；
2. **意图分类**：`kb_search` / `greeting` / `chitchat` / `follow_up`……
   非检索意图直接**跳过整段检索**（问候语不值得跑一遍向量检索）。

```
QUERY_UNDERSTAND ──> CHUNK_SEARCH ──> CHAT_COMPLETION
  【模型调用】          【代码算法】       【模型调用】
  改写 + 意图           非检索意图跳过      检索为空时直接对话
```

## 运行方式

```bash
python v2_query_understanding.py --eval --mock          # q8 翻正，6/9
python v2_query_understanding.py --query "你好" --mock  # 观察 greeting 意图跳过检索
python -m pytest tests/test_v2_query_understanding.py
```

## 代码走读

### 1. 安全默认值先行（↔ `query_understand.go:61`）

```python
state.rewrite_query = state.query  # 进门第一行
```

真实实现的第一行就是 `chatManage.RewriteQuery = chatManage.Query`。此后**任何
一步失败**——改写未启用（:64-71）、模型拿不到（:95-100）、调用出错（:125-131）、
输出解析不了——下游拿到的都是可用的原查询。改写是锦上添花，绝不能变成单点故障：
所有失败路径一律 `return next()` 降级，链条照走。

### 2. 结构化输出解析的三层容错（↔ `query_understand.go:321-407`）

LLM 被要求只输出 `{"rewrite_query":"...","intent":"..."}`，但生产代码从不假设
模型听话，`parse_structured_output` 逐层退让：

1. 整体按 JSON 解析（:349）；
2. 失败 → 截取首个 `{` 到最后一个 `}` 再试——容忍 markdown 代码块和多余文字
   （:353-359）；
3. 键名容错：`rewrite_query` 缺席时依次尝试 `rewritten_query`/`query`/`question`
   （:373-374）；
4. 还是失败 → 把**原始输出全文**当作改写结果（:336-340）——赌一把「模型直接
   输出了改写后的问题」；
5. 解析成功但 `rewrite_query` 为空 → 不覆盖默认值（:327-331）。

### 3. 意图门控（↔ `chat_manage.go:102-109`）

```python
def needs_retrieval(intent):
    return intent in ("kb_search", "clarification", "summarize", "")
```

空值视为需要检索是安全兜底——意图分类失败时宁可多检索。下游每个检索段插件
入口都做这个检查（对照 `rerank.go:41-43` 的 `if !chatManage.NeedsRetrieval()`），
v2 的 `PluginSearch` 学的就是这一笔。WeKnora 真实意图共 9 种
（`chat_manage.go:87-95`，含 web_search/image_only/doc_only 等），课程只实现
影响链路走向的子集。

### 4. 提示词与占位符渲染（↔ `rewrite.yaml` + `buildPrompts :283-315`）

真实提示词模板是 `config/prompt_templates/rewrite.yaml` 的 `default_rewrite`：
改写规则 + 意图分类决策表 + few-shot 示例 + `{{conversation}}` 进 system，
`{{query}}` 进 user。历史用 `------BEGIN------ / User question: / Assistant
answer: / ------END------` 块渲染（`formatConversationHistory` :444-459），
v2 逐字复刻这个格式。

一个开发时真实踩过的坑：模板里的 JSON 示例带字面量大括号，Python 的
`str.format` 会把它们当占位符直接抛异常——而且这个异常被「降级路径」静默
吞掉了，表现为改写永远不生效。这正是 WeKnora 用 `{{name}}` 手工替换
（`RenderPromptPlaceholders`）而不是模板引擎的原因；也是「降级路径必须留
日志」的原因（v2 在 `state.debug["understand_error"]` 里记录降级原因，
对照真实实现的 `pipelineError` 日志）。回归测试
`test_render_placeholders_tolerates_literal_braces` 钉死这个坑。

### 5. 模型调用参数（↔ `query_understand.go:121-122`）

`temperature=0.3, max_tokens=150`——低温度：改写要的是稳定复述，不是发挥；
150 token 上限：输出就一行 JSON，多给预算只会鼓励废话。

## 评测记录

`python v2_query_understanding.py --eval --mock`：**6/9**（v0/v1 为 5/9）。

| 变化 | 题 | 说明 |
|------|----|------|
| MISS → **PASS** | q8 | mock 伪 LLM 把「那超出之后呢？」补全成「免费版每月的消息配额是多少，那超出之后呢？」，faq-03 进入 top-3（rank 2） |
| 不变 | 其余 8 题 | 无历史 → 改写透传，检索结果与 v0/v1 逐字节一致（回归测试逐题守护） |

值得注意的细节：q8 救回来之后，词面上 faq-04（**专业版**配额）仍排在 faq-03
（免费版）前面——**改写救回的是召回，排序还是不完美**。排序质量是 v4 精排的
活，这里先埋个伏笔。

q3/q5/q7 依旧 MISS：改写帮不了它们——q7 需要真正的语义向量（v3 混合检索），
q3 需要更高召回与合并（v3/v5），q5 需要冗余抑制（v4）。

**Mock 伪 LLM 的边界**：`mock_understand_llm` 用固定规则模拟真实模型的三类
行为（问候/闲聊识别、拼接式省略补全、透传），确定性、可精确断言；但它只是
结构验证——真实 LLM 的改写会更自然（如直接输出「免费版消息配额超出后会
怎样？」），意图分类也远比词表匹配鲁棒。

## 这个版本证明了什么 / 牺牲了什么

**证明了**：
- 「往链上挂新插件」的开发模式成立——v2 没有改动 EventManager 一行代码，
  检索插件只改了两行（意图门控 + 改用 `rewrite_query`）；
- 检索前的一次 LLM 调用能救回整类问题（历史依赖），且失败时零成本降级。

**牺牲了（谁来补）**：
- 检索仍是单路词面/向量，q7（语义）、q6/q9（真实 embedding 下的关键词）
  各有一半盲区 → v3 混合检索 + RRF 融合
- 排序仍纯靠检索分：q8 里错误对象排在正确答案前面、q5 近重复无人抑制 → v4
- 历史只参与改写，没有作为上下文片段进入 prompt → v5 历史相关片段合并
